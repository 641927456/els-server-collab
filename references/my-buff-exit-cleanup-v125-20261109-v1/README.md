# Preserve the MyBuff iterator after native removal

This is the isolated support-source archive for [issue 976](https://github.com/641927456/els-server-collab/issues/976), based on the signed V124 component cohort. It adds `my_buff_cleanup.py` and `my_buff_cleanup.js`, connects their composer through `native_cache_sync.py`, and updates the compatibility profile's one existing and two new artifact bindings. Server business rules, Buff definitions, the original EXE and KOM resources are unchanged.

The same supported native image has a MyBuff cleanup defect: Cleanup calls the original per-key RemoveBuff, which erases its current map node, and then advances that erased node. The adapter changes only that subsequent iterator acquisition. Its private near stub reloads the first live node from the current owner map header and resumes the original loop check. The original UI cleanup prefix, virtual RemoveBuff, value destruction, map erase and epilogue remain in use. No native object or iterator is retained by JavaScript across calls or scenes.

The generator verifies the exact executable and mapped-image identities. The installer verifies the complete Cleanup and RemoveBuff bodies and the expected RemoveBuff virtual target before allocating or changing executable memory. It runs once from the existing owned native-cache initialization callback. A rejected installation reports `my_buff_cleanup_disabled` without disabling existing cache support. Executable stub storage remains retained, including after rollback or a controlled stop. `stop` and re-enable are owner-only operations for a quiescent fixture or teardown: they do not establish that an arbitrary running Cleanup is safe to stop. There is no production hot-toggle, polling loop or additional native entry hook.
