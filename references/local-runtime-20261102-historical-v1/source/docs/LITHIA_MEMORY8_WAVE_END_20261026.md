# MEMORY8 终点房：门是客户端的，服务端不该替它开门（35320/35321/35322）

> 本文取代同名的早前结论。早前版本判定「波次全灭 = 哨兵退役 = 房间该结束」，于是让客户端
> 的过门请求（0xbb）直接结算副本。实机反馈否定了这个判断：玩家要的是**穿过门去打 BOSS**，
> 而不是被结算送出去。本次把那条推断整条撤回。

## 玩家侧的事实

实机描述（截图 `clipboard-2026-10-25T17-06-29`，Lv93，右上「学会研究设施」，BOSS 血条 x18，
横幅「右边的大门打开了。可以通过大门移动到下一个区域。」）：

1. 清完这一间的小怪；
2. 把角色走到中间触发剧情；
3. 屏幕出文字、右边大门打开；
4. **玩家必须穿过这道门进入 BOSS 区**。

第 4 步过不去。所以"房间该不该结束"不是问题所在——**门本身没让玩家通过**。

## 证据链

会话 `20261026-004338`（服务端 `analysis/client-6c6b5180/20261026-004338/server-logs/server.jsonl`）：

| 时刻 | 事件 |
|---|---|
| 16:44:44 / 16:56:46 / 17:03:08 | 三次进入 35322（同一间房） |
| 17:03:10.062 | 静态 14 个 actor 落地：key0=9431(BOSS)、key1-3=9437/9438/9439、key4=9452、key5=9441、key6=9453、key7=9455、key8-13=9456/9457/9458 |
| 17:03:17.900 | 动态波次 8 只（9432）落地 |
| 17:03:22–17:03:39 | 8 条 0xad，全部是这 8 只波次 |
| 17:03:39.718 | 服务端发 0xba（房间条件被"波次退役哨兵"判为就绪） |
| 17:03:39.730 | 客户端 0xbb（**距 0xba 仅 12 ms，不是玩家走到门口才发的**） |
| 17:03:39.806→.807 | 0xbc + 0xc1（结算） |
| 17:03:46.467 | 0xa0（玩家离开副本） |

对照同一会话里 **30070（德鲁伊森林）** 的正常过门：

```
0xba → 0xbb → 0xbc → 0xb2(2936B，下一间的 actor 表) → 0xb3/0xb4/0xb5/0xb6/0xb7 → ...
```

差别只有一个：**0xbc 之后服务端有没有下一段可发**。30070 有，客户端就搬人；35322 的路线
`next` 是 `kind 4`（结束副本），服务端没有下一段，只能结算。

## 根因

`WAVE_RETREATS` 把「35322 的 9432 波次全灭」改写成了「9452 已退役」：

```python
run.retreated.update(...)   # finish_death -> wave_retreat
```

`condition_ready()` 的 kind 3 条件是 `dead or retreated`，于是房间在**客户端那边 9452 还站着**
的时候就判定为"已清"了。服务端据此发 0xba，客户端立刻回 0xbb，而房间真正的后续（9441 的
30000 血、9453、BOSS、9455）一件都还没打。

同一份代码的 `end_room_keys` 注释其实早就写对了：「The sentinel retires by its own script
**after the fight the opened gate leads to**」——门后那场战斗先发生，哨兵才退役。而
`WAVE_RETREATS` 抢在战斗之前把它退役掉了，这与它自己的注释互相矛盾。

早前两次尝试都是在错误前提上打补丁：

- 原始行为：0xbb 只回空 0xbc（判「门后的战斗还没发生」）→ 玩家在开着的门前干等 7 分钟（`20261026-000908`）；
- 早前修复：0xbb 直接结算 → 副本被提前结束，BOSS 没打、任务没进度（`20261026-004338`）。

两者都源于"服务端替客户端决定门开了"。而横幅和门本来就是客户端的：会话 `20261026-000908`
里服务端**一个 0xba 都没发**，客户端照样把横幅打出来了。

## 变更

- `els_server/domain/dungeon_flow.py`：`WAVE_RETREATS` 清空为 `()`，并改写顶部注释说明原因。
  波次死亡不再产生任何「哨兵退役」结论，`wave_retreat()` 恒返回 `()`。
  服务端不再为这三间房发 0xba，客户端自己的门继续可用。
- kind-4 分支保持原样（`retreated` 且未 `defeated` 时拒绝结算），作为安全网保留：只要哨兵没有
  真的离场，过门请求就不会结算房间。
- `tests/test_lithia_memory8_wave_retreat.py`：整份重写为「波次只是波次」的分裂断言——
  波次全灭不发通知、`retreated` 保持空、`condition_ready` 仍为假、0xbb 被忽略；
  以及反向路径——哨兵**真的**离场（`defeated`）之后房间才就绪、0xba 才发、0xbb 才结算。

## 边界

- 不白送任何东西：9452 从不进 `defeated` 由本路径产生，所以它的击杀掉落、经验、任务证明
  一条都不会因此发放。
- 只影响这三条路线的终点房；其余房间的推进规则未动。
- 本项**不保证**副本一定能结算。9452 是否真的会被客户端上报，取决于门后那场战斗会不会
  触发它的脚本退役。这一点只有实机才能验。
