## 闪退：一条上传包把连接打掉（本轮修好）

玩家报「游戏闪退」。两次掉线会话（`20261031-210307`、`20261031-212115`）的 `server-logs/server.jsonl` 结尾是同一行剧本：

```
13:24:14.127332 client_request  kind=2066 (0x812) size=96
13:24:14.127696 worker_error    ValueError('Guidebook flags size')
13:24:14.127981 connection_finished
```

也就是：客户端上传引导/教学标记（`0x812`，线包 96 字节）→ `guidebook_messages.request` 的 `len(payload)==4+5*count` 不成立 → `guidebook_flow.handle` **抛 `ValueError`** → `transport` 的兜底 `except Exception` 记 `worker_error` 并在 `finally` 里关掉连接 → 客户端 socket 一断，进程直接退出（没有弹窗，所以看着像"闪退"）。

关键点在这套分层：`transport` 只有 `ProtocolError`/`SessionOrderError` 算协议错误，**其余任何异常都会被当成致命错误关连接**。所以凡是「分派器被调用时抛 ValueError」的写法，在真机上等价于「客户端闪退」。`guidebook_flow.handle` 是唯一这么写的包处理器（`tests/test_guidebook.py` 还把这种 raise 当成契约锁住了）。

为什么现在才炸：`0x812` 在 20:29 及更早的会话里出现 **0 次**；21:03 与 21:21 各出现 1 次，且都是该会话最后一条请求。它跟衣橱能不能打开是同一件事——衣橱以前根本打不开，这条首次使用教学标记的路径从没被走到过。

修法（不改「raise 才是契约」的测试，只改两处）：

- `guidebook_messages.request` 的 size 检查从「必须恰好 `4+5*count`」放宽成「body 必须是 5 的整数倍，且不短于 count 声明的长度」，条目数量以字节实际携带的为准，每一条仍然校验 `index>0`、`opened∈{0,1}`、无重复。**短于声明仍然拒绝**（截断不能当整表覆盖），只是错误信息里带上 `len/count` 两个数。
- `local_session._handle` 在调用 `guidebook_handle` 外面包一层 `except ValueError`：丢掉这个包、保留会话、把原因写进 `self.guidebook_rejection`。`transport` 新增 `guidebook_diagnostic` 日志（`size` + `rejection`），下次再出现能直接看到真实形状。

同批还发现一个同类型的潜在雷：`local_bootstrap_clock.handle` 在 `phase=='new'` 时对畸形 `0xD92` 也抛 `ValueError`，同样会关连接。它只在 bootstrap 阶段生效、没被触发过，本轮**没动**，留作待办。

## 副本里那个只有「确认」的空白弹窗（0x460，本轮修好）

症状是进副本后每 30 秒弹一次无正文的白框，只有一个「确认」，且不挡操作。根因在
`local_session` 的 `0x460` 分支：`boosting_2026_essence.request()` 只认 **恰好 22 字节**的载荷，
而原生客户端发的是**线包 96 字节**；按 `encode_frame` 的固定开销换算，96 字节对应载荷 **25~32 字节**，
