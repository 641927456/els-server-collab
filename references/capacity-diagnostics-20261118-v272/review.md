# V272 capacity review

Approved rule: ordinary bags and life bag start at 40, existing capacities round up to complete eight-slot rows without losing purchased expansions or inventory. The original client masks an incomplete row; existing 36+8n values leave four inaccessible slots. The four-file candidate uses one shared base constant, migrates both capacity tables in the existing startup transaction, and preserves fixed fashion, furniture, ice, quick-slot and bank capacities. Explicit indexes/triggers are recreated after the copy. All 45 old values across seven groups, repeat migration, second-table rollback and actual startup/item-move boundaries have author evidence; four additional tests on the exact combined runtime cover real shop debit/receipt replay, transaction failure, life/new identity and UID-preserving last-row movement.

The no-schema alternative was evaluated but is not selected: it would introduce a second interpretation of stored capacity. No production database or runtime used it. Existing source consumers read saved_capacities/allowances; inventory_items now imports the same base instead of retaining a second 36 constant.

Migration changes stored capacities from 36+8n to 40+8n. A fresh SQLite API snapshot is required. After candidate code is armed, recovery must retain all four capacity files, so current items in the added slots remain usable. This is a forward-compatible recovery, not a way to undo the capacity behavior; a fault in those files requires repair with player data retained. No automatic database restoration is permitted. The installer must verify exact capacity changes and inventory identity after startup before admitting players. Local and online saves remain separate.

Two previously delivered V270 support JSON files are included only in the online delta; client files and native support are otherwise unchanged. Source delta is seven files, online delta nine. Three additional diagnostic files record bounded consumable rejection reasons and scene state, and three CP snapshot timing stages. They preserve eligibility, ACKs, debit/replay behavior, database queries and returned inputs/digests; four consumable checks and an owned read-only snapshot comparison passed. They add evidence for further investigation, not a demonstrated lag or damage-loss fix. The real UI fifth row and warehouse interaction await the installed candidate. This release does not establish natural acceptance for gate/potion/swallowed-damage reports, nor fix the independently observed native heap corruption. Original EXE/KOM are unchanged.
