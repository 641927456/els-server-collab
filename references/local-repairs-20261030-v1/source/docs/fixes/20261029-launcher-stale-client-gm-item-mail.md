# Stop counting terminated clients as running and issue GM items through the mailbox

Two local-tooling defects. (1) A terminated `x2_dx11.exe` keeps a process-list entry until every handle closes (zero threads/handles, no window). The launcher and both launch scripts matched on name alone, so the launcher reported "游戏运行中" and every 启动 press failed after a normal client exit. (2) The GM item form granted directly into `inventory_items`, so a granted item occupied a bag slot before the character had logged in.

Trigger: exit the client, then press 启动 again (blocked at the launcher, and again inside `probe_updated_client.py`); or grant an item from GM 工具 → 道具.

Fix: `launcher.service.exited(pid)` queries the process handle (`SYNCHRONIZE` + `WaitForSingleObject(0)`); a signaled handle means the process is gone even while the listing entry survives. An unopenable process is treated as running so a second client is never started. The launch scripts use the same rule through `launch_friends_client.running_clients()`, shared by `probe_updated_client.py` and `launch_friends_client.main`. GM item grants now build one validated instance, advance `inventory_sequence`, and write `game_mail` + `player_mail_meta` + `player_mail_items` escrow through the new `game_mail.local_item_campaign()` inside the launcher's existing transaction. Addressing uses `player_mail_meta` so only the selected character can see or claim the letter; unclaimed letters expire as a return to the same role. Quantity is bounded by the template stack size (one letter holds one instance). The character version fingerprint now includes the account's `game_mail` rows, so a stale form cannot grant twice.

Scope: launcher GM transaction, launcher copy, one additive mail-storage entry point. No client, protocol, schema or scoring change; the claim path is the existing `game_mail.claim` → `mail_attachments.claim` native route used by attendance mail.

Validation: `tests/test_launcher.py` — mailbox escrow/claim, single-role visibility, stack bound with no partial writes, idempotent retry, a terminated-process entry that no longer counts as running in either the launcher or `launch_friends_client.running_clients`. `test_launcher_v31/v32/v33/v37_v38`, `test_mail_scope_current`, `test_mail_actor_lifecycle_current`, `test_mailbox_admission` unchanged and passing. A live save probe confirmed an equipment letter claims back with full durability. On the affected machine the surviving entry (PID 23140, zero threads) is now ignored by both gates.

Runtime: the launch scripts are spawned per press, so 启动 picks up the fix without restarting the launcher; restart it only to load `launcher/service.py` changes (static assets reload on refresh). In-game mailbox rendering still needs a natural client session to accept.
