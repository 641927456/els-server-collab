# ELS 项目协作与发布规则

## 发布顺序（用户于 2026-10-15 指定）

所有功能修复默认按此顺序交付：**开发及必要检查 → 部署线上服务器测试 → 验证后同步并备份到本地单机版**。不要只改本地后就声称已交付；线上发布或验证尚未完成时明确标记状态。用户另有明确指示时以用户指示为准。

- 线上版本：`134.175.57.52`，部署目录 `C:\ElsFriends`，配置 `config/friends-server.toml`，游戏端口 TCP 19400。
- 本地单机版本：保留原单机账号、单机配置和 `G:\els\state\integrated.sqlite3`，与线上账号及存档独立。
- 共用修复使用同一不可变发布快照和发布编号，分别记录线上与本地清单、校验值、验证状态和备份位置。`releases/online/` 与 `releases/local/` 用于保存版本及当前版本指针。
- “上线测试”允许先运行必要的静态检查、临时数据库回归和服务器隔离副本检查；通过后优先部署到线上游戏服供玩家测试，再同步本地发布快照。协议验证、原生离线验证和玩家实战验收分别记录。
- 不把正在开发、缺少依赖或未通过检查的中间状态直接覆盖线上。跨会话先阅读各自修复记录和实际文件，冻结待发布快照，避免发布期间混入并行编辑；上线前复核线上来源版本。
- 发布前用 SQLite backup API 备份线上游戏库和账号库，并备份待替换代码、配置。正常停服，确认监听和计划任务均停止后替换、检查并重启。失败时优先回滚代码，恢复服务；不要自动回滚已有新数据的玩家库。
- 本地同步只同步代码、配表和所需资源证据；先备份本地旧版本。不要用线上玩家库覆盖单机库，也不要把本地库覆盖线上。账号令牌、密码、TLS 私钥和管理密钥不进入发布包。
- 保留新账号空角色列表、玩家自行建角命名、账号隔离和实验性组队开关。已删除的自动角色 `Player8` 不得随代码更新或旧库恢复重新生成。
- 现有反馈网页必须保持运行。不要停止/删除网页或不相关服务。不要关闭、接管或注入用户正在运行的游戏；需要玩家重新登录时告知即可。
- 同一时间只允许一个发布操作；其他会话的未发布工作保持独立。不得将“配表存在”或“协议通过”描述为全部功能/实战已验收。

## 工作目录

`G:\els` 是共享开发目录，不把其持续变化的内容自动视为已发布版本。完成修复后按上述顺序发布并更新版本清单。用户要求汇总其他会话时可以读取其记录；向其他会话发送消息仍需用户明确授权。
