# SQLite 写入争用与后续推进

对应 Issue #918。候选基于 Git main `64dc1d510e39b1c3e305616533f60d2300a7efff`，实际运行父版为 `native-quest-live-admission-20261107-v1`。只替换 source-bindings.json 的四个共享服务端叶；不把归档视作运行版本切换。

拾取和死亡写者原先在已取得写锁后最多连续准备 16 个请求。新实现保留无竞争时的批量 FULL 提交；有其他写者在 FIFO 等待且本次占锁已达约 4 毫秒时，在当前完整请求后提交，交出写锁。未处理的后缀留在本写者的有界 ready 队列，保留原顺序、角色归属和退出哨兵，下一次仍走原 FIFO。queue + ready + 正在执行的总容量没有扩大。4 毫秒是停止追加工作的软切片；单笔事务和 FULL 落盘不会被截断，不能当作延迟上限。

死亡结算的只读场景／经验来源 identity 在生产者持有角色域时、申请 SQL 写锁前生成。数据库归属、资格、经济变化、回执、编码检查和提交后状态采纳仍沿原入口。城镇移动缓冲与换图／退出的持久化屏障没有改动；拾取、死亡、过门不进入世界业务队列。

实际 SQLite 顺序对照已覆盖拾取与死亡两条 lane：旧版先执行剩余 8 条再交锁；候选先交给已等待的写者，剩余 8 条按顺序完成。测试同时覆盖已消费的退出哨兵、无竞争八请求单次提交、过期等待者清除和后来者不能插队。原奖励、称号、完整 SQL、幂等回执、预编码失败、实际提交失败、文件别名换绑和退出排空在签名 3.14t 运行时单独验证。

CI 的 tests/bootstrap.py 只为顺序单元隔离玩法依赖；运行真实修改后的 writer/SQLite 代码，使用真实 SQLite 文件。它不证明奖励正确或公网容量；这些以单独的实际运行回归和负载结果为准。

## 推进顺序

1. 本批：限制竞争批次占锁，保持事务和顺序，完成混合负载筛查。它管理 SQLite 单写者争用，不宣称变为多个并行 SQL 写者。
2. 下一批先修发送等待：缩短周期通知占连接 operation 的范围，补 C9 从预算等待到 drain 的统一截止时间；独立验证取消、断线、包序和场景代次。未通过前不切换 C9 限速实验。
3. 再做城镇选择／到达与后台轮询：分别记录 0x28、0x227 冷启动分位数和样本数，合并单次请求内重复投影，削减空闲 frontend 的实时唤醒。资格、库文件身份与写入后失效继续实时检查。
4. 同规格线上隔离环境再测内存与容量：区分 1.5 GiB 人工 Job 限制、真实保留对象和 4 GiB 主机余量。每个规模仍为 300 秒，20→30→40→50；超时、内存不足、丢包、落库或回执不符任一失败就停止扩大规模。5M 下同时记录城镇人数与广播量，不按总人数承诺容量。

新候选只在精确 head 合并审批和现有发布流程核收后安装。源码、签名运行组件、实际双端版本和公网容量分别登记，生产玩家库不恢复。

本地 4 核原生 TLS 筛查：20 城镇＋20 副本，每角色 300 秒，无 frontend。服务端拾取／死亡／配对门／B3 换图／城镇移动 P99 分别为 17／38／30／53／16ms，落库、ACK、最终坐标、排空及冷读通过；未经过公网。死亡最大约 249.7ms、城镇移动最大约 297.6ms，仍存在尖峰，不能据此标记线上 40 人或所有延迟已达标。
