# 单人退场的内部世界锁

已有 `solo_transition` 已将普通单人 `0x67` 退场送到准备队列，但 `FriendsSession._shared_request` 仍在内部世界锁里调用 LuCiel 退场处理器。预选角隔离后的50人短诊断中，该活动阶段锁样本最高53.52ms；仅扩大线程池不会移除这段内部锁。

修复继续先在世界锁内按原顺序执行前置共享路由，只对既有 `solo_transition` 认可的无房间/无组队/无挑战退场，将原生 LuCiel 处理器交回持账号域锁的调用者执行。原生处理器、事务、守卫、包构造及存档全部原样；提交后再在世界锁内调用原活动回复和相同的好友/业绩/师徒收尾。组队或其他上下文保持原路由。正常角色的后续原生处理继续复用原入口。

真实TLS对照中，人为暂停原SQL消费者时，旧版会挡住其他账号移动，新版仍能转发；两版均持账号域锁。原生68/D9载荷一致，真实出战状态变更和游标冷读成功，末次校验在SQL写后失败时完整回滚，重复退场不重写，225/227回城成功；C0、无GIL、无业务错误。原有四项共享副本/断线/UDP/新账号权限测试对私有候选重新通过。测试夹具曾错误假设默认active0必有实体行，随后又遗漏显式BEGIN，均只改自有夹具并保留原失败；未改产品容错或存档规则。

前后50人60秒混合诊断的原始广播为32/63→28/61ms，B3为31/43→28/29ms；短测不足以证明稳定改善。新区间没有活动阶段0x67的≥2ms世界锁样本，提交后的map_loading共享收尾仍有约5.87ms最大样本，明确保留。第一次提升检查错误禁止了这些必要收尾锁，已在未提升、未启动下一轮负载前修正为按阶段归因；延迟门限和原始样本没有变化。

新版短诊断还捕捉到coin-writer提交完成242.43ms、clock-writer完成203.54ms，其他写者门等待可达222.80ms；同期GC为0、事件环最大3.74ms。这证明此轮提交完成路径造成其他写者排队，未将其等同纯磁盘时间，也未据本机G盘结果断言线上C盘有同样成因。下一步须在实际线上硬件复核，FULL、提交后ACK和FIFO均保持。

CI用完整AST归一化限定这一处交接和原后处理提取，八个预选角状态和原有权限/事务合同继续保留。共享规则对false分支逐AST保持，原生和存储消费者逐SHA未变。完整五分钟新候选验证与公网验收各自记录，不复用旧候选的容量通过结论。
