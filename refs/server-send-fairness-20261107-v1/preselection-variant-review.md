# 未选角请求持世界锁

这是性能缺陷，未认定为权限绕过。线上 v34 的 20 次角色列表请求在世界队列执行，平均 19.59ms，P95/P99 25/40ms；原生阻塞对照进一步证明，该查询暂停时会阻塞其他账号的同城移动广播。

根因是 `_worker_call` 的默认世界锁包住整个原生处理，`LocalSession.handle` 的独立账号读取无法利用 `FriendsSession.handle` 已有的短世界锁段。搜索首先命中角色列表 `0x485`；沿同一个原生 rules 状态表扩展，确认另外五种前置握手也持有该外层锁。原生 `0x485` 的已接受条款重连及列表刷新也有同样问题。

| 范围 | 结果 | 处理 |
| --- | --- | --- |
| `0x485 / terms_ready` 精确入口 | 1 | 原生阻塞对照确认 |
| 同一状态表的预选角入口 | 6种请求、8个状态组合 | 仅无同账号 playing 租约且无成员/房间/挑战时隔离 |
| `0x1a / new` | 初始游戏角色尚未建立 | 保持原队列 |
| `0x28 / 0x6e9 / 0x5bf / 0x32 / 0x225 / 0x227` | 已有准备隔离 | 复用，未重复添加 |
| 已在线、组队、房间和挑战中的请求 | 涉及共享状态 | 保持原有路由和锁序 |

确认程度高，影响等级 P2。修复只扩展现有准备分类，并让重型 `0x485` 复用已有的2个准备名额。账号域锁、身份检查、条款接受写事务、原生规则/回复、成员操作和共享段世界锁均未变化，没有增线程池、缓存权限、跳过写盘或更改经济规则。

实际 TLS 测试覆盖13次原生处理：普通登录、角色列表刷新和已接受条款重连。对照全部持世界锁；修改后全部保留账号域锁但不持外层世界锁。查询被人为暂停时，另一账号的原生位置广播仍可送达，三个角色列表均与原构造器逐载荷相同。同账号活跃租约、frontend、无效事件和城镇阶段保留原路由。两轮独立存档均正常清理、C0、无GIL、无业务错误。

20人本地60秒混合负载的全部延迟及正确性门限通过，但不构成5分钟或公网容量结论。后续长测保留固定门限。CI 的 `verify_contract.py` 固定八个状态组合及无 playing 租约条件，归一化只允许这一个分类分支和 `0x485` 准备名额变化；其余工作者/业务/域锁 AST 与之前保持一致。
