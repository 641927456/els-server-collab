## 基线、调用与边界

Git blame 核过父版 AutoUpdate.cs 42–72 行的签名与旧 TLS 固定指纹逻辑。V83 保留 Verify、Latest、Download、缓存、反降级、激活及完整性方法的原代码，改动其共同 Open 传输，并移除旧主机的证书常量。新 GitHubUpdates 使用系统正常验证，没有全局或请求级放行证书的回调。搜索整个候选源未发现全局证书验证放行。

## 攻击场景与结果

1. 网络方或公开仓库写入者替换 latest.json/EXE：RSA 发布者签名、签名内精确大小/SHA256 仍要求一致。错误签名/渠道/文件名已由实际编译代码拒绝，匿名下载的真实 EXE 校验成功。私钥只在发布机读取，不嵌入程序或交给 CI。
2. GitHub 重定向到 HTTP、其他仓库、仿冒域名、非 443 端口、带用户信息或片段的地址：Allowed 在发出下一请求前拒绝。实际资源两跳下载使用默认 Windows TLS。策略负例覆盖域名后缀仿冒、错误仓库、HTTP、端口、userinfo、fragment、query。未使用恶意 TLS 测试服务器；证书链拒绝沿系统实现。
3. 分块包包含额外条目、重复文件、遗漏或跨清单文件：签名分块索引要求所有成员恰好覆盖原文件表一次；解包时核包 SHA/长度、完整条目集合和目标成员大小/SHA。已执行错误索引、损坏包、截断包测试，失败未修改旧指针。路径约束与拒绝链接的已有逻辑保留。
4. 稳定频道在清单与下载之间发生更新：EXE 地址按已验签版本与哈希前缀确定标签，不再从 latest 路径下载 EXE。反降级与 failed-activation 代码保持原字节，旧成功机制证据复用。
5. 发布脚本误覆盖不同包：已存在 GitHub asset 必须 state=uploaded、size 和 GitHub digest 与本地 SHA256 一致，否则停止；上传没有 --clobber。过长文件名的废弃资产只在相同 SHA 的短名称已上传后精确删除，旧候选从未设为启动器稳定渠道。
