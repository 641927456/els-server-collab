# 我的小屋宠物与原生房屋就绪流程审查

基线为 PR892 head `5367cd0123ec0e1bbe765687a8f33ccd612f6a57`。最终候选修改 16 个业务文件，新增其中 4 个模块。未修改原 EXE/KOM，也没有新增客户端运行组件。

原房屋入口未处理原生 92E 人员就绪请求，宠物放置列表始终为空。本次接通原生 92E/92F、A37/A38/A39/A3A/A3B、924 保存投影以及同一 SQL writer 中的放置、取回、完整周期成长结算与契约到期释放。这里只支持已批准的一层自有小屋和原始资源中的六种地垫。

审查重点是实际账号与当前角色、当前入房代次、道具和宠物归属、同 UID 重放、到期边界以及库存和奖励事务。放置不信任客户端时间或成长值；writer 获取后再采样服务端时钟。取回、成长保存、清除占位和回执在一个事务中完成，晚到的角色变化会回滚。旧召唤回执改为投影当前状态，并核对当前放置、远征和限时资格。旧限时宠物专用重放函数的唯一调用点已经替换，不保留两套实现。

共享 `owned_pet()` 在基线有 5 个引用文件；`companion_state` 有 12 个引用文件。审查移除了原候选对 `owned_pet()` 的广泛房屋限制：当前中韩官方说明只核实放置与限时、召唤、远征的互斥，没有核实所有喂食、成长和支持功能都必须禁用。本候选把房屋排除保留在召唤和远征入口，普通支持的原有资格不变，并覆盖已放置宠物的共享读取测试。参考：[国服家园说明](https://els.ztgame.com/game/000-1640-0030f-597049.shtml?ms=783)、[韩服家园指南](https://elsword.nexon.com/Info/Guide/View?n4ArticleSN=40)。

原生验证发现并修复一项会导致“保存成功但无法放置宠物”的缺陷：自由摆放家具由 244D960 创建模型，却未设置 Game+B00 的地垫绑定；格子摆放由 244D4A0/2451350 完成此绑定。v3 拒绝六种地垫的自由摆放记录，选择器只读取已验证的格子记录。其他家具的自由摆放入口保留。

认证 TLS 验证覆盖正常购买、放置和取回、原始回执重放、四槽容量、他人 UID、移除占用地垫、事务前角色切换、冷重登、完整周期成长、七天契约到期和永久升级。原生解析器覆盖完整 924、92F、真实 TLS 输出以及非空家具的运行时复制。源代码与各项脱敏结果的 SHA 见 qualified-summary 文件；原始报文和运行日志留在私有目录。

一个自有原始 Game 使用现有签名运行组件完成 923/92E 入房、格子地垫初始化、A38 放置生成原生宠物实体、A3A 取回移除实体，并观察 120 秒。四项原生 pending gate 均成功，服务端没有错误；提前取回没有增加成长，ED、经验、库存和普通登录城镇均保持。该原生运行使用 v2；最终 v4 收紧失败的自由摆放分支，并移除未经核实的全局支持限制，正常格子输入的执行路径未改。变化覆盖在最终 writer/deadline 结果中。依照项目的结果复用规则，不重跑未变原生场景。

此前测试失败均保留：准备城镇未对齐；观察器误把实体字段当成角色 UID；观察器误以角色 UID 搜索地垫宠物；以及自由摆放地垫没有原生绑定。没有放宽服务端资格或扩大超时处理这些失败。

本审查未发现上述范围内尚未处理的可操作安全缺陷。当前目录不含 Git 元数据，历史上下文以精确基线文件比较为准；本文件不构成 GitHub 人工审批。仍未验证自然 GUI、他人小屋访问、楼层扩展和原生离开小屋，不能据此宣称整个房屋系统完成。尚未合并 main、安装双端或更新线上进度。
