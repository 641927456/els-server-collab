# First-town native task HUD notification

The default saved town previously satisfied the starter arrival objective at
character selection, before a newly created role completed its tutorial. The
first real town load then had no completion edge to notify the original HUD.

This independent candidate changes two existing server leaves. Normal new,
unprogressed tutorial roles start with an active objective count of zero. The
committed tutorial clear and normal 227 town arrival supply the real progress
edge; the existing progress transaction pre-encodes full F0 and F3 records
before commit. Existing ready/completed and unknown historical state is kept.
No quest reward is claimed automatically and the central Quest window is not
forced open. Native HUD preferences and visibility remain authoritative.

The user explicitly chose the right-side task name and completion indication,
then opening details and claiming manually. Verification covers real private
Application/TLS for four starter roots, actual LOCAL mode, duplicate/cold
loading, transaction encode-failure rollback/retry, and old-state fixtures.
Private tutorial combat inputs and the clock seam are controlled validation;
the native consumer is established statically. Natural GUI/battle is untested.

This is source-only and is not deployed. The protected delivery order is P0
tutorial admission hotfix, then M1, then this HUD correction. After M1 completes,
the maintainer must bind the then-current online/local parents and all manifest
hashes, the exact P0 module, both unchanged HUD parent leaves, the exact M1 HP
module, and the actual P0/M1 completion chain. The earlier exact-P0 gate is a
historical source qualification probe, not a delivery parent after M1. An old
P0 rollup must never replace the newer M1 package.
